# Design

## Context

- Требования - в `specs/keep-in-touch/spec.md`, мотивация - в `proposal.md`.
- Сейчас в `contacts` нет ничего про общение. Список (`src/app/page.tsx`) одним запросом берёт контакты и число заметок, сортирует по имени; поиск - `ilike` по имени. Список рисует клиентский компонент `contact-list.tsx`, которому сервер отдаёт простые строки данных - так сделано ради скорости на 1000 контактов.
- Формы добавления и изменения используют общий `contact-fields.tsx` и server actions в `src/app/actions.ts`.
- Миграции: `drizzle-kit generate` пишет SQL в `drizzle/`, на сервере их применяет разовый контейнер `migrate` до старта нового образа (`deploy/deploy.sh`).
- В проекте нет компонента выбора из списка (shadcn `Select` требует новую библиотеку `@radix-ui/react-select`).

## Goals / Non-Goals

**Goals:**
- Правило «пора связаться» считается в одном месте - в SQL-запросе, - чтобы метка и сортировка в списке и метка в карточке никогда не расходились.
- Список остаётся одним запросом к базе, без загрузки всех контактов в память ради сортировки.

**Non-Goals:**
- Фоновые задачи, расписания, уведомления.
- История общений (отдельная таблица) - по решению «только сегодня, без истории».

## Decisions

### 1. Два новых поля в `contacts`

- `contact_frequency` - `text`, может быть пустым (`NULL` = «Не задана»). Значения: `week`, `two_weeks`, `month`, `quarter`, `half_year`, `year`. Допустимые значения ограничены `CHECK`-ограничением в схеме Drizzle.
- `last_contacted_at` - `timestamp with time zone`, может быть пустым (`NULL` = «ещё не отмечали»).

Почему не отдельная таблица общений: истории не нужно, достаточно последней даты. Почему не число дней: нужен календарный месяц/год («1 октября → 1 ноября»), а 30 дней дали бы сдвиг. Почему `text` + `CHECK`, а не `pgEnum`: добавить новое значение потом - простая миграция, без особенностей `ALTER TYPE`.

Миграция добавляет два nullable-столбца без значений по умолчанию - существующие строки получают `NULL`, данные не теряются.

### 2. Частота → интервал Postgres

В коде одна таблица соответствий значение → подпись на русском → интервал Postgres (`'7 days'`, `'14 days'`, `'1 month'`, `'3 months'`, `'6 months'`, `'1 year'`). Срок следующего общения: `last_contacted_at + interval`. Календарная арифметика Postgres сама обрабатывает «31 января + 1 месяц».

### 3. Где считать «пора связаться»

В запросе списка и в запросе карточки - одно и то же SQL-выражение, собранное одной функцией в коде (например, в `src/db/keep-in-touch.ts`):

- `due_at` = `last_contacted_at + interval(frequency)` (или `NULL`);
- `is_due` = `frequency IS NOT NULL AND (last_contacted_at IS NULL OR due_at <= now())`.

Сравнение - с текущим моментом (`now()`), а не с началом дня: «общались в 15:00, раз в неделю» → метка появится через 7 суток в 15:00. Это проще и не зависит от часового пояса сервера; на глаз разница в пределах одного дня.

Альтернатива - считать в JavaScript после загрузки: отвергнута, потому что сортировка тогда требует загрузить все контакты, а правило может разъехаться между страницами.

### 4. Сортировка списка

`ORDER BY`:
1. `is_due DESC` - «пора связаться» первыми;
2. среди них: сначала ни разу не отмеченные (`last_contacted_at IS NULL`), потом по `due_at ASC` (раньше наступил срок - дольше ждёт - выше);
3. `name ASC`.

Для не-«пора» пункты 2 не влияют (`due_at` у них в будущем или `NULL`, но сначала выравниваются выражением `CASE WHEN is_due ...`), поэтому они идут по имени, как раньше. Поиск по имени - тот же запрос с `WHERE`, поэтому правило работает и в поиске.

Порядок «ни разу не отмеченные - первыми» - моё решение (в спеке зафиксировано сценарием): у них нет даты, и логично считать, что они ждут дольше всех.

### 5. Кнопка «Пообщались»

Новый server action `markContacted(contactId)`: `UPDATE contacts SET last_contacted_at = now()`, `revalidatePath` для `/` и карточки. Время берётся на сервере (`now()` в базе), а не из браузера. Отдельный клиентский компонент-кнопка с `useActionState`, как у других форм, показывает «Сохраняю…» во время запроса. Подтверждения нет - действие безопасное, повторное нажатие просто обновляет дату.

`addNote` не трогает `last_contacted_at` (по требованию).

### 6. Выбор частоты в форме

Нативный `<select name="frequency">` внутри `contact-fields.tsx`, стилизованный теми же классами и токенами, что `Input` (рамка `border-ink`, `bg-card`, фокус `ring`). Без новой библиотеки. Сервер проверяет, что пришло одно из допустимых значений или пусто; иначе - ошибка «Неизвестная частота общения».

Альтернатива - shadcn `Select` (`@radix-ui/react-select`): красивее выпадающий список, но это новая зависимость, которую по правилам проекта надо отдельно согласовывать. Можно заменить позже без изменения спеки.

### 7. Отображение

- `formatDate` (только дата, без времени) добавляется в `src/lib/format.ts` рядом с `formatDateTime`.
- Карточка: новый блок «Связь» под контактными данными - частота, «Последнее общение: …» / «ещё не отмечали», «Следующий раз: …» (если частота задана), метка «Пора связаться» и кнопка «Пообщались».
- Список: `ContactListItem` получает поле `isDue: boolean`; метка - бейдж в том же стиле, что счётчик заметок, но с акцентным токеном (`bg-red`/`text-ink` или `bg-pink`), с иконкой из уже подключённого `lucide-react`.

### 8. Тестовые данные

`seed.ts` при заполнении задаёт частоту примерно трети контактов и случайную дату последнего общения (или пусто) у части из них, чтобы в списке было видно и «пора связаться», и «ещё рано».

## Risks / Trade-offs

- [Даты показываются в часовом поясе сервера (в Docker - UTC), как и время заметок сейчас] → для пользователя в Москве дата «Последнего общения» после 21:00 может показаться завтрашней. Тот же эффект уже есть у заметок; если станет мешать - отдельная правка с явным часовым поясом.
- [Сортировка по вычисляемому выражению не использует индекс] → на тысячах контактов это доли миллисекунды; индекс по `name` остаётся для поиска.
- [Ошибочное нажатие «Пообщались» нельзя отменить] → осознанное продуктовое решение; дату можно лишь перезаписать следующим нажатием.

## Migration Plan

1. `pnpm db:generate` создаёт `drizzle/0001_*.sql` с двумя `ALTER TABLE ... ADD COLUMN` и `CHECK`.
2. Локально - `pnpm db:migrate` (или `db:push`, как в README).
3. На сервере - как обычно: merge в main → образ → контейнер `migrate` применяет миграцию → новый образ → smoke `/health`.
4. Миграция только добавляет столбцы, старая версия приложения с ними продолжает работать. Ручной откат приложения на предыдущий образ безопасен; столбцы можно оставить.
