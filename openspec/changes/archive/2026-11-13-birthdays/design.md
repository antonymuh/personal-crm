# Design

## Context

- Требования - в `specs/contact-birthdays/spec.md` и `specs/data-ownership/spec.md`, мотивация - в `proposal.md`.
- Контакт - таблица `contacts` в `src/db/schema.ts`. Формы добавления и изменения используют общий `src/components/contact-fields.tsx`; разбор и проверка формы - `parseContactForm` в `src/db/contact-form.ts`, до транзакции: ошибка формы ничего не пишет.
- Главная `src/app/page.tsx` - серверная страница: список одним запросом `listContacts` из `src/db/contact-list.ts`, затем клиентский `ContactList`.
- Карточка `src/app/contacts/[id]/page.tsx` получает контакт через `getContact` (`src/db/contacts.ts`) со всеми колонками.
- Даты сейчас форматируются в `src/lib/format.ts` через `Intl.DateTimeFormat("ru-RU")` без часового пояса, то есть в поясе процесса. В контейнере на сервере это UTC.
- В проекте нет работы с часовыми поясами, кроме таймера бэкапа (`Europe/Moscow`).
- Тесты: Vitest на тестовой базе (`test/db.ts`), миграции проверяются на отдельной базе (`test/owner-migration.test.ts`), e2e - Playwright на собранном приложении с настоящей базой и Mailpit (`e2e/`). Правило: тест раньше кода, у каждого сценария свой тест.

## Goals / Non-Goals

**Goals:**
- Одно правило «когда следующий день рождения, через сколько дней и сколько исполнится» для блока и карточки, без расхождений.
- Всё, что зависит от даты, проверяется Vitest с подставленным «сегодня», без ожидания нужного дня.
- Миграция только добавляет колонку.

**Non-Goals:**
- Метка дня рождения в общем списке контактов, сортировка списка по дням рождения.
- Свой часовой пояс у пользователя: для всех - Москва.
- Уведомления любого вида.

## Decisions

### 1. Колонка `birth_date` типа `date`, в коде - строка `YYYY-MM-DD`

`contacts.birth_date date null`, в Drizzle `date("birth_date", { mode: "string" })`.

- Тип `date` хранит только день, без времени и пояса. Строка `YYYY-MM-DD` не сдвигается при переходе через пояса, в отличие от `Date`: дата «15 ноября» в UTC-контейнере не превратится в «14 ноября».
- Альтернатива - `timestamp`. Отвергнута: у дня рождения нет времени, а пояс дал бы сдвиг на день.
- Альтернатива - отдельные поля день и месяц. Отвергнута: год обязателен, вы выбрали полную дату.

Миграция `drizzle/0004_*.sql` - один `ALTER TABLE "contacts" ADD COLUMN "birth_date" date;`. Без `DEFAULT`, без `NOT NULL`, существующие строки не переписываются. Индекс не нужен (решение 3).

### 2. «Сегодня» - по Москве, и передаётся параметром

`src/lib/today.ts`: `moscowToday(now = new Date()): string` возвращает `YYYY-MM-DD` в поясе `Europe/Moscow` через `Intl.DateTimeFormat` с `timeZone`. Это встроено в Node и браузер, новых библиотек нет.

- Все функции, которым нужно «сегодня», получают его параметром. Страница и server actions вызывают `moscowToday()`, тесты подставляют любую дату, включая 28 декабря и 25 февраля високосного года.
- Альтернатива - `now()` в SQL. Отвергнута: Postgres на сервере в UTC, а подставить другой день в тесте нельзя.
- Альтернатива - переменная `TZ` у контейнера. Отвергнута: меняет всё приложение и зависит от окружения, а тест её не увидит.

### 3. Правило дня рождения - чистые функции в `src/lib/birthdays.ts`

Без импорта базы и `server-only`: их используют и сервер, и клиентская форма.

- `parseBirthDate(value, today)`: пусто → «не задана»; не `YYYY-MM-DD` или такой даты нет в календаре (31 февраля) или раньше `1900-01-01` → «Некорректная дата рождения»; позже `today` → «Дата рождения не может быть в будущем». Проверка «настоящая дата» - собрать дату из частей и сравнить части обратно.
- `ageOn(birthDate, today)`: сколько полных лет.
- `nextBirthday(birthDate, today)`: `{ date, daysUntil, turning }`. День рождения в году `today`; если он уже прошёл - в следующем году. 29 февраля в невисокосный год → 28 февраля. Дни считаются разницей дат в UTC, без перехода на летнее время.
- `whenLabel(daysUntil)`: «Сегодня», «Завтра», «Через N дней».
- `turningLabel(daysUntil, turning)`: «исполняется N» в сам день, иначе «исполнится N».
- `yearsLabel(n)`: «21 год», «22 года», «25 лет»; склонение через `Intl.PluralRules("ru")`, как и «Через 2 дня / 5 дней».
- Форматирование «15 ноября 1990» и «15 ноября» - в `src/lib/format.ts`, с `timeZone: "UTC"`, чтобы строка `YYYY-MM-DD` не сдвигалась.

### 4. Выборка блока: свои контакты с датой - в базе, окно и порядок - в коде

`listUpcomingBirthdays(userId, today, executor = db)` в `src/db/birthdays.ts`:

1. Один запрос: `id`, `name`, `birth_date` контактов пользователя, где `birth_date is not null`. Поиск и группа не передаются вообще - блок от них не зависит.
2. Для каждого `nextBirthday(...)`, оставить `daysUntil <= 7`, сортировать по `daysUntil`, затем по имени (`localeCompare("ru")`).

- Альтернатива - считать всё в SQL. Отвергнута: правило 29 февраля и перехода через год пришлось бы писать второй раз, на SQL, и держать две версии одинаковыми. У одного пользователя порядка тысячи контактов; три поля на контакт - это мелочь даже без индекса.
- Фильтр `userId` - в том же `where`, как во всех запросах: чужие контакты не попадают в выборку (сценарий «Скоро день рождения» в `data-ownership`).

### 5. Форма и сохранение

- `ContactForm.fields` получает `birthDate: string | null`. `parseContactForm` вызывает `parseBirthDate` до транзакции, поэтому при ошибке не меняется ничего, ни имя, ни прежняя дата.
- `createContactFromForm` и `updateContactFromForm` получают `today` последним параметром со значением `moscowToday()`: server actions не меняются, тесты подставляют свой день.
- Пустое поле при изменении записывает `null` - так дата стирается.
- В `contact-fields.tsx` - `<input type="date" name="birthDate" min="1900-01-01" max={today}>` с подписью «Дата рождения». `today` приходит с сервера: главная и карточка передают его в `AddContactDialog` и `EditContactDialog`. Календарь браузера - только удобство, решает сервер.
- В `EditContactDialog` - текущая дата контакта в `defaultValue`.

### 6. Интерфейс

- Блок `src/components/upcoming-birthdays.tsx` - серверный компонент без состояния: заголовок «Скоро день рождения» (`h2`), список ссылок на `/contacts/<id>`. В строке: имя, «Завтра · 14 ноября», «исполнится 26»; иконка `Cake` из `lucide-react` (библиотека уже в проекте). Стиль - существующие токены (`rounded-sketch`, `shadow-pop-*`, `border-ink`), как у карточек списка.
- Место - на главной между заголовком «Контакты» и поиском. Пустой результат - компонент не рендерится.
- Карточка: строка «День рождения: 15 ноября 1990 (35 лет)» с иконкой `Cake` в основной карточке, после «Откуда знакомы». Подсказка «Контактных данных пока нет» учитывает и дату рождения.

### 7. Тесты

- Vitest без базы - `src/lib/birthdays.test.ts`, `src/lib/today.test.ts`: проверка даты, возраст и склонение, окно и подписи, переход через год, 29 февраля, Москва после полуночи по UTC.
- Vitest с базой - `src/db/contact-form.test.ts` (сохранить, изменить, стереть, ошибки ничего не меняют), `src/db/birthdays.test.ts` (окно, порядок, без даты, чужие контакты, поиск и группа не влияют).
- Миграция - `test/birthdays-migration.test.ts` по образцу `test/owner-migration.test.ts`: база на схеме до `0004`, контакты с заметками и группами, применить миграции → у всех `birth_date` пустая, остальное как было.
- Playwright - `e2e/birthdays.spec.ts`: ввод, изменение и стирание даты; блок с контактом «Завтра»; переход в карточку; блок при поиске и группе; нет блока без дней рождения; в Mailpit нет писем, кроме входа. «Сегодня» в e2e - `moscowToday()` в момент теста: приложение в браузере живёт в настоящем времени. Сценарий двух пользователей - в `e2e/two-users.spec.ts`.

## Risks / Trade-offs

- [e2e около полуночи по Москве: тест посчитал «завтра» в 23:59:59, а страница открылась в 00:00:01] → в e2e брать дни рождения не на границе окна (завтра и через 3 дня), точные границы проверяет Vitest с подставленной датой.
- [Календарь браузера в разных браузерах выглядит по-разному, в старых Safari его нет] → сервер всё равно проверяет дату; поле принимает ввод `ГГГГ-ММ-ДД`.
- [Пользователь не в Москве увидит «сегодня» по Москве] → вы согласились; при другом поясе смещение - не больше суток.
- [Тест-стенд - копия прода без дат рождения] → проверку на стенде делаем, введя дату руками; seed даёт даты только локально.

## Migration Plan

1. Миграция `0004` только добавляет пустую колонку. Данные не меняются, поэтому показывать её до merge по `CLAUDE.md` не обязательно, но SQL будет виден в PR.
2. Выкатка как обычно: на стенде и на проде миграция идёт отдельным контейнером до старта нового образа, на проде перед ней бэкап.
3. Откат через Deploy prod с галочкой «откат»: старый образ не знает о колонке и просто её не читает; колонка и введённые даты остаются в базе и вернутся при следующей выкатке. Откатывать миграцию не нужно.
