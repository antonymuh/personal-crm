# Design

## Context

- Требования — в `specs/contact-groups/spec.md`, мотивация — в `proposal.md`.
- Список (`src/app/page.tsx`) собирается одним запросом Drizzle прямо в странице: поиск — `ilike` по имени, порядок и метка «пора связаться» — из `src/db/keep-in-touch.ts`. Клиентский `contact-list.tsx` получает простые строки данных (так сделано ради скорости на 1000 контактов).
- Формы добавления и изменения используют общий `contact-fields.tsx` и server actions из `src/app/actions.ts`. Диалоги построены на `useActionState` и показывают ошибку из `ActionResult`.
- Поиск (`contact-search.tsx`) пишет в адрес только `?q=` и затирает остальные параметры.
- Автотестов в проекте пока нет. Vitest уже указан в стеке в `CLAUDE.md`. Действует правило TDD: тест раньше кода, у каждого сценария свой тест.
- Локальная база — Postgres в Docker (`docker-compose.yml`), строка подключения — `DATABASE_URL` в `.env`.

## Goals / Non-Goals

**Goals:**
- Каждый сценарий спеки проверяется автотестом на Vitest, который запускается командой `pnpm test` за секунды, без браузера.
- Тесты, которым нужна база, работают с настоящим Postgres, но с отдельной тестовой базой: рабочие контакты не трогаются.
- Список остаётся одним запросом к базе, вместе с фильтром и метками групп.

**Non-Goals:**
- e2e-тесты (Playwright) и CI — следующие шаги модуля.
- Отдельная страница управления группами, цвета или порядок групп, фильтр по нескольким группам сразу.

## Decisions

### 1. Модель данных: две таблицы

- `groups`: `id serial`, `name text not null`, `created_at`. Уникальный индекс по `lower(name)` гарантирует, что «Теннис» и «теннис» не уживутся вместе, даже если две вкладки сохраняют одновременно.
- `contact_groups`: `contact_id` → `contacts.id`, `group_id` → `groups.id`, оба с `ON DELETE CASCADE`, первичный ключ `(contact_id, group_id)`. Удалили контакт или группу — членство исчезает само, а контакты и группы остаются.

Альтернатива — массив названий в `contacts`. Отвергнута: переименование и удаление группы пришлось бы делать по всем контактам, а уникальность и целостность не обеспечить средствами базы.

Миграция только добавляет таблицы, существующие данные не меняются.

### 2. Логика отдельно от страниц, чтобы её можно было тестировать

- `src/lib/groups.ts` — чистые функции без базы: нормализация и проверка названия (обрезать пробелы, пустое — ошибка), разбор отмеченных групп из формы, разбор параметра фильтра из адреса. Их проверяют быстрые unit-тесты.
- `src/db/groups.ts` — работа с базой: список групп по алфавиту, «найти или создать по названию», выставить группы контакта, переименовать, удалить. Функции принимают соединение или транзакцию.
- `src/db/contact-list.ts` — запрос списка `listContacts({ query, groupId })`, перенесённый из `page.tsx`, и `getContactGroups(contactId)` для карточки.
- Server actions в `actions.ts` остаются тонкими: читают форму, вызывают эти функции, делают `revalidatePath` или `redirect`.

Почему так: server actions зависят от `next/cache` и `next/navigation`, и тестировать их напрямую можно только через моки, то есть тестировать реализацию. Функции данных проверяются на настоящей базе и проверяют поведение.

### 3. Сохранение контакта с группами — одна транзакция

`createContact` и `updateContact` выполняют в одной транзакции: запись контакта, «найти или создать» новую группу, замену набора групп контакта (удалить старые связи, вставить отмеченные). Если что-то упало, не остаётся ни «полуконтакта», ни созданной впустую группы. Проверка имени контакта и названия новой группы делается до транзакции: при ошибке в базу ничего не пишется (сценарий «Ошибка в форме не теряет группу»).

«Найти или создать» — `INSERT ... ON CONFLICT DO NOTHING` по уникальному индексу и затем выборка по `lower(name)`. Так нет гонки между двумя одновременными сохранениями.

Отмеченные группы приходят из формы как список id. Id, которых уже нет в базе (группу удалили в другой вкладке), молча отбрасываются.

### 4. Список: фильтр и метки в том же запросе

- Метки: подзапрос `json_agg` названий групп контакта, отсортированных по алфавиту, — поле `groupNames: string[]` в строке списка.
- Фильтр: `?group=<id>` в адресе; в запросе — `exists (select 1 from contact_groups where ...)`. Порядок — тот же `keepInTouchOrder`, поэтому правило «пора связаться» внутри группы работает само.
- Страница отдельным маленьким запросом берёт список групп (для фильтра и форм). Если `group` из адреса нет среди групп, фильтр считается равным «Все».

### 5. Интерфейс

- Фильтр — ряд кнопок-ссылок над списком: «Все» и группы. Ссылки сохраняют `q`, поиск сохраняет `group`: `contact-search.tsx` начинает переносить существующий параметр `group`. Ссылки — обычные `<Link>`, без клиентского состояния. Если групп нет, фильтр не рисуется.
- При выбранной группе рядом с фильтром есть кнопки «Переименовать» (диалог с одним полем) и «Удалить» (диалог подтверждения). Обе построены по образцу существующих `edit-contact-dialog` и `delete-contact-dialog`. После удаления — `redirect("/")`.
- В форме контакта — блок «Группы»: галочки (`<input type="checkbox" name="groupIds">`) и поле «Новая группа». Новых библиотек нет: нативные чекбоксы, стилизованные токенами.
- Метки групп — небольшой бейдж в стиле счётчика заметок, общий для списка и карточки (`group-badges.tsx`).
- Списки групп для форм приходят пропсом со страницы: `AddContactDialog` и `EditContactDialog` получают `groups`, а `EditContactDialog` ещё и текущие `groupIds` контакта.

### 6. Vitest и тестовая база

- Зависимости: `vitest` (последняя стабильная версия, проверить при установке). Дополнительных плагинов нет: алиас `@/` → `src/` задаётся в `vitest.config.ts`, `server-only` подменяется пустым модулем.
- `pnpm test` → `vitest run`.
- Тестовая база — `personal_crm_test` в том же локальном контейнере Postgres. Адрес выводится из `DATABASE_URL` заменой имени базы, поэтому новых строк в `.env` не нужно. Перед прогоном `globalSetup` создаёт базу, если её нет, и применяет миграции из `drizzle/`. Защита: если имя базы не оканчивается на `_test`, тесты не запускаются.
- Каждый тест с базой начинает с пустых таблиц (`TRUNCATE ... RESTART IDENTITY CASCADE`). Файлы с базой выполняются последовательно, чтобы не мешать друг другу.

Альтернатива — моки базы в unit-тестах. Отвергнута: тест повторял бы устройство запросов, а не проверял поведение. Сценарии вида «контакт виден в фильтре» мок не проверит.

### 7. Как сценарии покрываются тестами

- Название группы, разбор формы и фильтра — unit-тесты `src/lib/groups.test.ts`.
- Создание, «найти или создать», членство, переименование, удаление, каскад при удалении контакта, фильтр, поиск вместе с фильтром, порядок, метки (`groupNames`), «группы больше нет» — тесты функций данных на тестовой базе (`src/db/*.test.ts`).
- Сценарии чистого отображения («фильтр не показывается, когда групп нет», «галочки отражают текущие группы», «Передумал» в диалоге удаления, «другой браузер») проверяются на уровне данных, которые получает интерфейс: пустой список групп, `groupIds` контакта, отсутствие изменений без вызова удаления, хранение в базе. Сам вид на экране сейчас проверяется руками; e2e на основные пути добавятся следующим шагом модуля.

### 8. Тестовые данные

`seed.ts` создаёт группы «Семья», «Друзья», «Знакомые», «Теннис», «Аналитики» и раскладывает по ним примерно половину контактов (по 1–2 группы). `--reset` очищает и группы.

## Risks / Trade-offs

- [Для `pnpm test` нужен запущенный Docker с Postgres] → тот же контейнер, что для `pnpm dev`. Если база недоступна, тесты падают с понятным сообщением. В CI будет свой Postgres (следующий шаг).
- [Тесты с базой медленнее чистых unit] → таблиц мало, очистка быстрая; ориентир — секунды на весь набор.
- [Перенос запроса списка из `page.tsx` в `src/db/contact-list.ts`] → поведение не меняется, порядок и метка «пора связаться» берутся из того же `keep-in-touch.ts`. Новые тесты на порядок это подтверждают.
- [Метки групп увеличивают ответ списка на 1000 контактов] → это несколько коротких строк на контакт; данные остаются плоскими, как и сейчас.

## Migration Plan

1. `pnpm db:generate` создаёт `drizzle/0002_*.sql` с двумя новыми таблицами и уникальным индексом.
2. Локально — `pnpm db:migrate`.
3. На сервере — как обычно: merge в main → образ → контейнер `migrate` применяет миграцию → новый образ → smoke `/health`. По заданию модуля пуш будет после настройки CI.
4. Миграция только добавляет таблицы: ручной откат на предыдущий образ безопасен, таблицы можно оставить.
