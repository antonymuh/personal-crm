# Личная CRM

Приложение для ведения контактов людей, которых я знаю лично: кто это, откуда
знакомы, телефон, почта и заметки о договорённостях. Продуктовая идея и критерии
успеха — в `specs/01-продуктовая-идея.md`.

## Стек

- Next.js (App Router) + TypeScript
- React, Tailwind CSS, shadcn/ui
- PostgreSQL (в Docker), Drizzle ORM
- Vitest и Playwright (автотесты), Prettier (формат кода)
- pnpm

Данные читаются и пишутся только на сервере (Server Components + Server Actions).
Браузер к базе не обращается.

Вход — по ссылке из письма (Better Auth), паролей нет. Каждый пользователь видит
только свои контакты, заметки и группы. Письма отправляет Nodemailer: на вашем
компьютере и в автотестах — в почтовый ящик-заглушку Mailpit, на сервере — через
Resend. Куда именно, решает строка `SMTP_URL` в `.env`.

## Что нужно заранее

- Node.js 20+
- pnpm
- Docker Desktop (для локального PostgreSQL и почтовой заглушки Mailpit)

## Запуск

```bash
# 1. Установить зависимости
pnpm install

# 2. Создать .env из примера и вписать в него значения
cp .env.example .env        # Windows PowerShell: Copy-Item .env.example .env
#    В .env придумайте пароль для POSTGRES_PASSWORD и подставьте его же
#    в DATABASE_URL (формат строки подсказан в .env.example).
#    Для входа: BETTER_AUTH_SECRET — любая длинная случайная строка
#    (openssl rand -base64 32), BETTER_AUTH_URL=http://localhost:3000,
#    SMTP_URL=smtp://localhost:1025, OWNER_EMAIL — ваша почта

# 3. Поднять PostgreSQL и Mailpit в Docker
docker compose up -d

# 4. Создать таблицы в базе (применить миграции из drizzle/)
pnpm db:migrate

# 5. (по желанию) наполнить тестовыми данными — 1000 контактов и 5 групп
#    у пользователя с почтой OWNER_EMAIL.
#    Работает только на пустой базе: если контакты или группы уже есть, команда остановится
pnpm db:seed

# 6. Запустить приложение
pnpm dev
```

Откройте http://localhost:3000 — появится страница входа. Письма со ссылкой
приходят не в настоящий ящик, а в Mailpit: http://localhost:8025. Войти можно
под любым адресом — так удобно проверять нескольких пользователей.

## Как проверить руками

Вход:

1. Открыли `/` без входа — страница входа: «Вход», поле «Почта», кнопка
   «Получить ссылку». Прямой адрес карточки контакта тоже ведёт сюда.
2. Ввели « Anna@Example.COM » — «Ссылка для входа отправлена на
   anna@example.com», форма осталась. В Mailpit письмо от «Личная CRM»
   с темой «Вход в Личную CRM», кнопкой «Войти» и сроком 15 минут.
3. Ввели «anna@» — под полем «Проверь адрес почты», письма нет.
4. Запросили ссылку на одну почту 4 раза подряд — на 4-й «Слишком часто,
   попробуй через несколько минут», в Mailpit 3 письма.
5. Нажали «Войти» в последнем письме — вы внутри, в шапке почта и «Выйти».
   Новый адрес — пустой список «Пока нет контактов. Добавьте первый.»
6. Открыли то же или более раннее письмо ещё раз — «Ссылка устарела, запроси
   новую», кнопка «Получить новую ссылку» ведёт на страницу входа.
7. Вошли под той же почтой во втором браузере — внутри в обоих. «Выйти»
   в одном — второй остался внутри.
8. Анна (обычное окно) добавила контакт и группу «Теннис», Борис (окно
   инкогнито, другая почта) — их нет ни в списке, ни в поиске, ни в фильтре;
   адрес карточки контакта Анны у Бориса — «Контакт не найден». Борис создаёт
   свою группу «Теннис» — у каждого своя.

Контакты (после входа):

1. Открыли `/` — виден список всех контактов и их количество.
2. Нажали «Добавить контакт», заполнили имя — контакт появился в списке.
3. Нашли контакт через поиск по имени, открыли карточку, дописали заметку —
   заметка сохранилась и видна в карточке.
4. Открыли тот же адрес в другом браузере, войдя под той же почтой — те же
   контакты (данные в базе).
5. Открыли «Изменить» у контакта, выбрали «Частота общения: Раз в месяц»,
   сохранили — в карточке в блоке «Связь» видна частота, «Последнее общение:
   ещё не отмечали» и метка «Пора связаться». В списке контакт стоит наверху
   с той же меткой.
6. В карточке нажали «Пообщались» — «Последнее общение» стало сегодняшним,
   «Следующий раз» — через месяц, метка пропала. В списке контакт вернулся
   на своё место по алфавиту.
7. Дописали заметку — дата последнего общения не изменилась.
8. Поменяли частоту на «Не задана» — метка «Пора связаться» не появляется,
   сколько бы времени ни прошло.
9. В «Добавить контакт» вписали «Новая группа: Теннис» и сохранили — над списком
   появился фильтр «Все» и «Теннис», у контакта метка «Теннис» в списке и в карточке.
10. В «Изменить» у другого контакта отметили «Теннис» и вписали новую группу
    «Семья» — у контакта обе метки.
11. Выбрали фильтр «Теннис» — в списке только его контакты, в адресе
    `?group=…`. Ввели имя в поиск — фильтр сохранился.
12. При выбранной группе нажали «Переименовать» — новое название видно в фильтре,
    в формах и в метках. «Удалить» → «Оставить» — ничего не изменилось;
    «Удалить» → «Удалить» — группы нет, контакты на месте, показан весь список.

## Полезные команды

- `pnpm dev` — запуск в режиме разработки
- `pnpm build && pnpm start` — продакшен-сборка
- `pnpm test` — автотесты (Vitest). Нужен запущенный Docker с базой
  (`docker compose up -d`). Тесты сами создают отдельную базу `personal_crm_test`
  в том же контейнере и работают только с ней — ваши контакты не трогают
- `pnpm test:e2e` — тесты в настоящем браузере (Playwright). Тоже нужен Docker
  с базой и Mailpit. Собирают приложение, запускают его на http://127.0.0.1:3100
  с отдельной базой `personal_crm_e2e_test` и проходят вход, главный сценарий,
  группы и «Пора связаться». Ссылки входа берут из Mailpit, поэтому перед каждым
  тестом его ящик очищается. `pnpm dev` на порту 3000 при этом можно не останавливать.
  Перед первым запуском один раз: `pnpm exec playwright install chromium`
- `pnpm format` — привести код к единому формату (Prettier);
  `pnpm format:check` — только проверить
- `pnpm db:migrate` — применить миграции из `drizzle/` к базе так же, как при
  выкатке. Миграция входа отдаёт уже существующие контакты, заметки и группы
  пользователю с почтой `OWNER_EMAIL`; без неё на базе с данными остановится
  и ничего не изменит
- `pnpm db:push` — применить схему к базе напрямую, без миграций (только для
  пустой базы)
- `pnpm db:generate` — сгенерировать SQL-миграцию из схемы
- `pnpm db:seed` — заполнить пустую базу тестовыми данными (1000 контактов,
  5 групп) у пользователя с почтой `OWNER_EMAIL`
- `pnpm db:seed --reset` — **удалить все контакты, заметки и группы** и заполнить базу заново
- `pnpm db:studio` — веб-интерфейс к базе (Drizzle Studio)
- `docker compose down` — остановить базу и Mailpit (данные базы сохраняются
  в volume, письма в Mailpit — нет)

## Проверки на каждый PR (CI)

На каждый pull request GitHub Actions запускает (вкладка **Checks** в PR):

- **Lint, format, types, unit tests** — ESLint, Prettier, TypeScript, Vitest;
- **E2E (Playwright)** — тесты в браузере. Если упали, отчёт со следами
  (trace) — в Actions → нужный запуск → Artifacts → `playwright-report`;
- **Docker image build** — образ собирается так же, как при выкатке, но никуда
  не отправляется;
- **Security audit** — уязвимости в зависимостях.

База в CI своя, одноразовая, внутри запуска. Красный CI — PR не вливаем,
чиним причину.

## Выкатка на сервер

- **Тест-стенд** — автоматически: любой push в ветку `main` выкатывает новую версию
  на стенд.
- **Прод** — только кнопкой **Deploy prod** (см. «Выкатить на прод»). На прод едет
  тот же образ, что прошёл стенд.

| Окружение              | Адрес                                       | Папка на сервере   |
| ---------------------- | ------------------------------------------- | ------------------ |
| Тест-стенд (`staging`) | https://test-app.pocketcrm.co (под паролем) | `/opt/crm/staging` |
| Прод (`prod`)          | https://app.pocketcrm.co                    | `/opt/crm/prod`    |

Что происходит после push в `main` (видно во вкладке **Actions** на GitHub, запуск **Deploy**):

1. GitHub Actions собирает Docker-образ приложения и кладёт его в GHCR
   (`ghcr.io/antonymuh/personal-crm`, тег — хеш коммита). Один образ на оба окружения.
2. Вся папка `deploy/` копируется на сервер в папку стенда.
3. На сервере `deploy.sh staging <версия>`: скачивает образ → применяет миграции
   разовым контейнером → запускает новую версию → проверяет `/health`.
   Упали миграции — новая версия не запускается, работает старая.

Выкатка на прод (запуск **Deploy prod**) идёт так же, только на проде перед
миграциями `deploy.sh` снимает бэкап базы: не снялся — новая версия не запускается.
Две выкатки на одно окружение одновременно не идут: вторая ждёт первую.

### Выкатить на прод

1. Проверьте новую версию на стенде https://test-app.pocketcrm.co. В Actions
   запуск **Deploy** для этого коммита должен быть зелёным.
2. GitHub → **Actions** → слева **Deploy prod** → справа **Run workflow**.
3. Поле **SHA** оставьте пустым, галочку **Rollback** не ставьте → **Run workflow**.
   Выкатится версия последней зелёной выкатки на стенд.
4. Дождитесь зелёного запуска. Какая версия выкатилась — в итогах запуска
   (открыть запуск → **Summary**), там же ссылка на коммит.
5. Откройте https://app.pocketcrm.co и пройдите главный сценарий.

Запасной путь — вписать в поле **SHA** хеш нужного коммита (можно первые 7 символов).
Выкатка пройдёт, только если этот коммит уже был зелёным на стенде, иначе запуск
остановится с ошибкой и прод не изменится.

В списке выкаток GitHub (Deployments) у прода стоит коммит, с которого запущен
workflow, — это последний коммит `main`, а не обязательно выкаченная версия.
Точная версия — в итогах запуска и на сервере: `cat /opt/crm/prod/.current-tag`.

### Откатить прод

Вернуть версию прода, которая работала до текущей:

1. GitHub → **Actions** → **Deploy prod** → **Run workflow**.
2. Поставьте галочку **Rollback**, поле SHA не важно → **Run workflow**.
3. В итогах запуска — на какую версию откатились. Проверьте https://app.pocketcrm.co.

Прошлую версию помнит сервер (`/opt/crm/prod/.previous-tag`), стенд при откате
не проверяется, образ берётся с сервера. Откат меняет только версию приложения,
**база остаётся как есть**: поля, которые добавила новая версия, остаются в базе,
старая версия их просто не показывает. Повторный откат вернёт версию, с которой
откатились. Если новая версия испортила данные — нужен откат вместе с базой (ниже).

### Чистка старых образов

После каждой удачной выкатки на прод:

- в GHCR остаются 10 последних сборок, более старые удаляются;
- на сервере удаляются образы старше 2 недель, кроме текущей и прошлой версии
  прода (нужны для отката) и текущей версии стенда.

Пока на GitHub не задана переменная `DEPLOY_HOST`, выкатка пропускается —
только собирается образ.

### Настройки на GitHub (Settings → Secrets and variables → Actions)

- Переменные: `DEPLOY_HOST` (IP сервера), `DEPLOY_USER` (пользователь на сервере).
  Адреса окружений записаны в `.github/workflows/deploy.yml` (стенд) и `deploy-prod.yml` (прод).
- Секреты: `DEPLOY_SSH_KEY` (ключ деплоя), `DEPLOY_KNOWN_HOSTS` (отпечаток сервера)

### .env на сервере

У каждого окружения свой файл: `/opt/crm/prod/.env` и `/opt/crm/staging/.env`,
права 600. Какие строки нужны — в `deploy/.env.example`. Значения у окружений
разные: свой пароль базы, свой `BETTER_AUTH_SECRET`, свой ключ Resend.

Для входа нужны четыре строки — их вписываете вы **до** выкатки версии со входом:

- `BETTER_AUTH_SECRET` — результат `openssl rand -base64 32`;
- `BETTER_AUTH_URL=https://app.pocketcrm.co`;
- `SMTP_URL=smtps://resend:<ключ>@smtp.resend.com:465` — ключ Resend с доступом
  только на отправку и только для домена `mail.crm.pocketcrm.co`;
- `OWNER_EMAIL` — ваша почта: все контакты, заметки и группы, которые были
  до входа, станут вашими. Без неё миграция остановит выкатку, старая версия
  продолжит работать.

### Если выкатка упала

Во вкладке Actions шаг Deploy красный — новая версия не заработала.
Автоматического отката нет. Прод откатывается кнопкой: **Deploy prod** с галочкой
**Rollback** (см. «Откатить прод»). Если миграции уже прошли и поменяли данные,
откатывать надо вместе с базой — см. «Откат версии вместе с базой» ниже.

Стенд откатывается вручную на сервере:

```bash
ssh crm
cd /opt/crm/staging && ./deploy.sh staging "$(cat .previous-tag)"
```

### Логи на сервере

Логи приложения, базы и миграций прода и стенда пишутся в журнал сервера (journald).
Они переживают выкатку, откат и перезагрузку сервера. Размер журнала ограничивает
система: не больше 10% диска, самые старые строки удаляются сами.

Читать логи на сервере (`ssh crm`):

```bash
sudo journalctl -t prod-app-1 --since "1 hour ago"        # приложение прода за последний час
sudo journalctl -t prod-app-1 -f                          # смотреть вживую, выход — Ctrl+C
sudo journalctl -t prod-app-1 -p warning --since today    # только ошибки и предупреждения за сегодня
sudo journalctl -t prod-db-1 -n 50                        # последние 50 строк базы
sudo journalctl COM_DOCKER_COMPOSE_PROJECT=prod COM_DOCKER_COMPOSE_SERVICE=migrate -n 50   # миграции
sudo journalctl COM_DOCKER_COMPOSE_PROJECT=prod --since today   # всё окружение сразу
```

Для стенда — то же самое с `staging`: `staging-app-1`, `staging-db-1`,
`COM_DOCKER_COMPOSE_PROJECT=staging`.

### Изменения схемы базы

Поменяли `src/db/schema.ts` — выполните `pnpm db:generate` и закоммитьте новые
файлы из `drizzle/`. На сервере миграции применятся сами при выкатке.

## Бэкапы базы

Бэкапы базы прода лежат на сервере в `/opt/crm/prod/backups`, читать их может
только владелец (внутри личные данные). Бэкапов два вида, у каждого хранятся
7 последних, более старые удаляются сами:

- **Перед выкаткой** — снимает `deploy.sh` перед каждой выкаткой на прод.
  Имя: `<дата>_<время UTC>_before-<версия>.dump`, например
  `2026-11-06_153000_before-c4d5d2a.dump`. Версия в имени — та, что работала
  **до** выкатки: этот бэкап подходит именно к ней.
- **Ежедневный** — каждый день в 03:00 по Москве (00:00 UTC). Имя:
  `<дата>_<время UTC>_daily.dump`. Запускает таймер systemd `crm-prod-backup`
  (файлы в `deploy/systemd/`), его ставит и обновляет сама выкатка на прод.
  Если сервер был выключен в 03:00, бэкап снимется сразу после включения.

Копии, которые снимает `restore.sh` (`before-restore-…`), сами не удаляются.

Проверить ежедневный бэкап:

```bash
ssh crm
systemctl list-timers crm-prod-backup.timer   # когда следующий запуск
journalctl -u crm-prod-backup -n 20           # как прошёл последний
/opt/crm/prod/backup.sh                       # снять бэкап прямо сейчас
```

Посмотреть бэкапы:

```bash
ssh crm
ls -lh /opt/crm/prod/backups
```

## Восстановление базы из бэкапа

Запускаете только вы, руками на сервере. Восстановление **удаляет текущую
базу** и загружает бэкап в новую пустую.

```bash
ssh crm
cd /opt/crm/prod
ls -lh backups                     # выбрать файл
./restore.sh backups/<файл>.dump
```

Что делает скрипт:

1. Показывает, какой файл загрузит, какую базу заменит и какая версия приложения
   сейчас работает. Ждёт, пока вы введёте `yes`. Любой другой ответ — выход,
   ничего не меняется.
2. Снимает копию текущей базы: `backups/<время>_before-restore-<версия>.dump`.
3. Останавливает приложение, удаляет базу, создаёт заново, загружает бэкап.
4. Запускает ту же версию приложения и проверяет `/health`. Версию не меняет.

Если restore упал — приложение остановлено, скрипт напишет, где копия базы
из шага 2. Вернуть её: `./restore.sh backups/<эта копия>.dump`.

### Откат версии вместе с базой

Нужен, если выкатка поменяла данные (например, миграцией) и новую версию надо
убрать. Порядок важен — сначала версия, потом база:

1. Запомните версию, которую откатываете: `ssh crm cat /opt/crm/prod/.current-tag`.
2. **Deploy prod** с галочкой **Rollback** — вернётся прошлая версия приложения.
3. Найдите бэкап, снятый перед выкаткой откатываемой версии
   (`before-<прошлая версия>`), и верните базу — поднимется уже прошлая версия:

```bash
ssh crm
cd /opt/crm/prod
ls -lh backups
./restore.sh backups/<этот файл>.dump
```

На шаге 2 `deploy.sh` тоже снимет бэкап — это копия базы после неудачной
выкатки, на всякий случай.

## Тест-стенд

https://test-app.pocketcrm.co — копия приложения для проверки руками перед продом.
Живёт на том же сервере, но отдельно: своя база, свой `.env`, свой ключ почты.

- **Пароль на весь сайт.** Браузер спросит логин `crm` и пароль стенда. Внутри
  копия данных прода, поэтому без пароля стенд не открывается.
- **Вход независим от прода.** Ссылка во входном письме ведёт на `test-app.`,
  кука входа живёт только на своём адресе: вход на стенде не трогает вход на проде.
- **Письма настоящие**, через Resend, со своим ключом `staging`.
- **База — копия прода** из последнего бэкапа. Испортилась — пересоздаём (ниже).
  Бэкапы стенда не снимаются.

### Пересоздать базу стенда из бэкапа прода

Удаляет текущую базу стенда и загружает в неё самый свежий бэкап прода. Прод не трогает.

```bash
ssh crm
/opt/crm/staging/refresh-staging.sh                          # самый свежий бэкап прода
/opt/crm/staging/refresh-staging.sh /opt/crm/prod/backups/<файл>.dump   # или конкретный
```

### Сменить пароль стенда

```bash
ssh -t crm 'printf "crm:%s
" "$(openssl passwd -apr1)" | sudo tee /etc/nginx/test-app.pocketcrm.co.htpasswd >/dev/null && sudo chown root:www-data /etc/nginx/test-app.pocketcrm.co.htpasswd && sudo chmod 640 /etc/nginx/test-app.pocketcrm.co.htpasswd && echo готово'
```

Пароль спросит дважды, на экране он не виден.

### Как стенд устроен на сервере

- Приложение и база — docker compose проект `staging`, приложение на `127.0.0.1:3001`.
- nginx: `/etc/nginx/sites-available/test-app.pocketcrm.co.conf` (копия в
  `deploy/nginx/`), свой сертификат `test-app.pocketcrm.co` — продлевается сам,
  как и сертификат прода.
- У контейнеров обоих окружений лимит памяти 512 МБ: стенд не может отъесть память у прода.
